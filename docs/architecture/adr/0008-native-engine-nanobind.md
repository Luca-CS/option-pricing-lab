# ADR-0008: The native engine as a nanobind wheel

- Status: Accepted, 7 November 2026

## Context

The C++/CUDA engine (CMake, C++17, CUDA 12.9) was a shared library with a C API, loaded by `ctypes` through
structures copied field by field from its header: a field added on one side and not the other was silent memory
corruption, and the library was found by path.

## Decision

- `packages/native` builds the engine with **scikit-build-core** and exposes it through a **nanobind** module,
  `optlab.native._ext`: typed arguments, NumPy arrays without copies, sizes checked against the request, the GIL
  released while the engine runs, C++ exceptions raised as `optlab.core.engines.EngineError` with the engine's
  message.
- The requests are checked C++ structures (`requests.hpp`, `requests.cpp`) that throw; a static `optlab_engine` links
  into the module and into the C++ tests.
- CMake options: `OPTLAB_WITH_CUDA` (OFF builds the CPU engines only), `OPTLAB_CUDA_ARCHS` (`native`, `portable`), and
  the nvcc flags chosen by the ablation (`-prec-div=false -prec-sqrt=false -ftz=true`, no `--use_fast_math`,
  `__expf`/`__logf` off).
- A typed stub (`_ext.pyi`) is generated by nanobind and versioned; `test_stub.py` fails when it drifts. pyright reads
  the stub, so CI type-checks without compiling.
- Builds: Windows (MSVC 2022) and Linux (gcc, in the worker image). CI builds the CPU-only module on both and runs the
  CPU engine's tests; the GPU tests run on the machine.
- The fallback to NumPy stays explicit, with its reason, through the engine registry
  ([ADR-0004](0004-dependency-direction.md)).

## Consequences

- Prices did not move: the same C++ code runs, and the golden numbers of the CPU and GPU engines held bit for bit
  through the change; times stayed within 2 %.
- `uv sync` builds the module (about 80 s with CUDA for one architecture) and rebuilds it only when `packages/native`
  changes.
- nanobind and scikit-build-core are build dependencies of `optlab-native` only.

## Alternatives considered

- **Keep ctypes**: no build step in Python, but the duplicated structures were the main reliability risk of the
  bridge.
- **pybind11**: mature, larger binaries and slower compiles; nanobind is its successor by the same author, with
  first-class ndarray support and stub generation.
- **Cython or cffi**: still a hand-written mirror of the C structures.
